# M11 — Motel Operations 2.0

Рабочая сцена: `Assets/Game/Scenes/Motel_Blockout_V3.unity`. Unity 6000.3.19f1 / URP 17.3 / NGO 2.13.3 / Unity Transport 2.6.0. Пакеты не менялись, внешние assets не загружались.

## Запуск и проверка вручную

1. Дважды открыть `Builds/Playtest/LaunchWindowed.command`, расположить окна 800×600 рядом. **Start Host** в первом, **Start Client** во втором, `127.0.0.1:7777`. Альтернатива: Host в Unity Play Mode и Client в этой же версии standalone.
2. За Reception открыть компьютер через **E**, нажать **Start Shift**. Управление прежнее: WASD, мышь, Shift, E; Esc закрывает компьютер или освобождает курсор вне него.
3. В любом номере сделать кровать и собрать два предмета мусора. Номер остаётся Dirty. Возле письменного стола появится один тёмный мешок. Взять его через E, выйти через лобби и отнести в контейнер справа снаружи, около края парковки. **E — Dispose Trash** завершает мусорную часть уборки. Если кровать сделана, номер становится Ready.
4. Попросить второго игрока подобрать мешок, собранный первым. Проверить видимый мешок у напарника. Отключить несущего Client: мешок должен вернуться к точке выдачи исходного номера. Повторно подключиться и закончить уборку.
5. Полотенце и мешок занимают одно место переноски. При занятой руке подсказка объясняет, что нужно завершить текущую доставку. Отмена звонка не удаляет несвязанный мешок. Контейнер не принимает полотенца.
6. Во время смены один из номеров может потерять электричество. В нём выключится существующий локальный Light. На доске и компьютере появится POWER FAULT; свободный такой номер недоступен для регистрации. Если жилец находится внутри, неисправность может занять свободную телефонную линию.
7. Для ремонта пройти в Utility за Reception: на южной стене находится панель с четырьмя подписями номеров. Навести на соответствующий выключатель и нажать **E — Reset Breaker XXX**. Свет восстановится на всех клиентах; связанный звонок завершится, даже если никто ещё не ответил.
8. Альтернатива для занятого неисправного номера: в компьютере **Relocate Guest — Room XXX**, затем выбрать другой Ready номер с исправным электричеством. Второй игрок наблюдает физический выход, проход по коридору и вход гостя. Целевой номер сразу резервируется; источник после выхода становится Dirty и сохраняет неисправность. Переселение не продлевает проживание.
9. Принять ключ вернувшегося гостя через прежний checkout. Убрать номер повторно, включая новый мешок. Закончить 15-минутную смену, посмотреть общую статистику и начать следующую без переподключения.

Для обычного теста не нужны специальные параметры запуска. Диагностические сценарии включаются только явными аргументами Development build.

## Состояние и ответственность

- `ServiceRoom.RoomSnapshot` сохраняет Dirty / Ready / Occupied. Добавлены фаза мешка, несущий клиент, состояние электричества с отдельным `FaultId`, флаг сообщения об аварии и узкая резервация переселения. Все поля записывает сервер. Очистка комнаты считается завершённой после кровати, обоих предметов и утилизации.
- `TowelCarrier` сохранён и расширен одной атомарной `CarrySnapshot`: None / CleanTowel / GarbageBag, ссылка на исходный номер и Cycle. Визуальные мешки — обычные дочерние объекты существующего player prefab, без дополнительных NetworkObject и физики. Имена существующего компонента и towel API сохранены для совместимости.
- `RoomOperationsInteraction` — только настроенный E-target для мешка или автомата. `GarbageDumpster` использует прежние `PlayerInteractor` / `IInteractable` и `ServiceInteractionValidation`. Сервер сверяет фактическое положение своего представления игрока, коллайдер, видимость, владение предметом, номер и актуальный цикл.
- `GuestServiceRequests` по-прежнему держит один активный запрос. Электрическая неисправность может сообщиться один раз на FaultId, отдельно от одного обычного запроса на проживание. Активный towel/TV запрос не вытесняется; авария остаётся видимой на доске и ждёт свободной линии. Ремонт не зависит от принятия звонка. TV repair остаётся отдельной механикой.
- `GuestLifecycle` расширен фазой Relocating. Существующий NavMeshAgent, NetworkTransform, дверные проходы и анимации сохранены. `ReceptionDesk.RequestRelocateRpc` проверяет владельца computer lease, гостя/Visit, оба Cycle, FaultId и доступность. Сначала резервирует цель. При выходе источник становится Dirty, назначение переключается на цель; при физическом достижении GuestIdle цель становится Occupied. Исходный StayEndsAt сохраняется; если он истёк в пути, гость после прибытия возвращается по обычному checkout-маршруту.
- Во время переселения checkout этого гостя недоступен. Повторный запрос не создаёт вторую операцию. Исходный неисправный номер нельзя заселить до ремонта и уборки. При очистке смены резервации и маршруты снимаются.
- Незавершённый запрос старого номера отменяется при переселении; чужой запрос остаётся. Связанные полотенца очищаются; мешки других номеров сохраняются. Уже использованный обычный запрос переносится как лимит текущего проживания, автоматически повторно не создаётся.
- `NightShiftController` владеет расписанием аварий и новыми итоговыми счётчиками. Check-in/checkout теперь считаются в соответствующих успешных транзакциях, а не по любой смене RoomStatus: переселение не увеличивает их ошибочно. Prepared по-прежнему считается по Dirty → Ready; добавлены мешки, аварии/ремонты и завершённые переселения.
- Доска и компьютер читают перечисленные состояния; отдельной базы заданий нет.

## Настройка нагрузки

| Inspector | Значение | Назначение |
|---|---:|---|
| Shift Duration | 900 с | Прежняя смена 22:00–06:00 |
| Arrival Count | 6–8 | Сохранённый диапазон прибытий |
| First Arrival Delay | 85 с | Больше времени на первые наружные рейсы |
| Arrival Patience | 150 с | Компенсация дополнительного времени уборки |
| Call Delay / Between Requests | 30 / 20 с | Меньше наложения обычных задач |
| Electrical Fault Count | 1–2 | Максимум запланированных аварий |
| Fault Window | 0.30–0.72 | Аварии в средней части смены |
| Electrical Seed | 0 | Новый seed; ненулевой фиксирует электрическое расписание |

Сервер заранее распределяет моменты аварий по окну. Одновременно существует только одна неисправность. Следующая ждёт ремонта и паузы до 45 с, а после 72% смены новые аварии не начинаются. Из-за незавершённого ремонта фактических аварий может быть меньше запланированных. При наличии подходящего занятого номера выбор в 75% случаев идёт из занятых; в остальных — из всех доступных для аварии. Зарезервированные номера исключены. Ненулевой seed воспроизводит выбор при одинаковом ходе игрового состояния, но не фиксирует действия игроков или расписание прибытий.

Это стартовая настройка, не результат внешнего балансировочного плейтеста. Время наружного рейса создаёт выбор между уборкой, стойкой и ремонтом; новых штрафов или ролей нет.

## Сцена и сохранность проекта

Добавлен корень `MotelOperations`: четыре точки мешков, четыре автомата в Utility и наружный контейнер. Мешок — небольшой low-poly Mesh, созданный Editor-инструментом один раз; существующий тёмный материал. В player prefab добавлены только два визуальных мешка и ссылки carry-компонента. Runtime-позиции берутся из настроенных объектов, а не из координат в gameplay-скриптах.

Используются четыре существующих `Room10X_Light`. Их исходные параметры, глобальное освещение, материалы, геометрия, мебель и парковка сохранены. Выключается только enabled соответствующего источника. Ambient и свет из соседних зон остаются: номер не превращается в абсолютную темноту. Запечённое освещение не перестраивалось.

Резервная копия: `Backups/BeforeMotelOperationsM11_20261025_130600/`. Точный аудит изменений и результаты тестов — в соседних `change-audit.json` и `verification.md`. Git-коммит не создавался.

`Tools → Motel → Validate Motel Operations M11` проверяет сохранённую сцену и ссылки. `Tools → Motel → Build Current Playtest` выполняет прежние проверки и M11, затем заменяет `Builds/Playtest/MotelGame.app`. Setup запускается только явным запросом; обычный domain reload не перестраивает сцену.

## Ограничения

Один предмет на игрока, без выбрасывания, передачи в руки, физики мусора или общего inventory. Один телефонный запрос глобально. Один fault одновременно. Нет сохранения сессии, host migration, online lobby, Relay или Steam-интеграции. Движение игроков остаётся owner-authoritative как в прежнем прототипе; серверные проверки действий используют реплицированное положение, это не новая система защиты от перемещения читом.

Игрок может физически перекрыть путь NPC. Гость ждёт освобождения прохода; не телепортируется сквозь препятствия. Удобство интерфейса, ощущение управления, различимость затемнения, положение мешка у рук, слышимость телефона и работа между двумя LAN-компьютерами требуют ручного плейтеста.

## Воспроизводимые автоматические проверки

Из корня проекта, после сборки текущего Playtest:

```sh
python3 Documentation/MotelOperationsM11/Tests/run_operations_test.py --night
python3 Documentation/MotelOperationsM11/Tests/run_operations_test.py --graphics
python3 Documentation/MotelOperationsM11/Tests/run_operations_test.py --edges
```

`--night` проходит настоящие 900 секунд и следующую 180-секундную смену. Сохранены обычные параметры прибытий и обслуживания; seed фиксирован, первые обычные запросы выбираются так, чтобы гарантированно проверить TV и полотенце. Аварии создаёт штатное расписание.

Без `--night` / `--edges` запускается целевой сценарий 600 +180 секунд с тремя краткими late-join клиентами. Для воспроизводимости только время/номер диагностических аварий вызываются через валидируемую серверную операцию; перед стартом меняются параметры нагрузки и проживания. `--edges` использует короткую смену для конкурирующих запросов от двух игроков в допустимой зоне и сброса активных задач. `--graphics` добавляет окна и снимки; без него экземпляры работают headless.

Порты 17791/17792/17793 отделены от обычного7777. Тестовые игроки ходят через CharacterController, взаимодействуют через реальные raycast/RPC, а NPC — через штатный NavMeshAgent. Состояния комнаты, владение мешком, резервации, позиции NPC и сроки проживания не подменяются. Файловые сигналы координируют тестовых акторов, но не передают игровой state. Все журналы сохраняются в `Documentation/MotelOperationsM11/`; история диагностических неудач остаётся на месте.

Эти сценарии доступны только в Editor/Development и запускаются явными аргументами. Обычный запуск игры их не создаёт. Полный перечень фактически завершённых запусков, их настройки и ограничения — в `verification.md`.
